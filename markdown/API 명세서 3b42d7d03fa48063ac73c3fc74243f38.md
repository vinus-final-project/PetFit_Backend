# API 명세서

# API 개요

| 항목 | 내용 |
| --- | --- |
| Protocol | HTTPS |
| Architecture | REST API |
| Request Format | Multipart Form Data (영상 업로드), JSON |
| Response Format | JSON |
| 인증 | 없음. 기기 식별자(`X-Device-Id`)로 데이터를 분리한다 |
| 분석 처리 | **비동기**. 요청 접수 후 폴링으로 상태를 조회한다 |
| 이력 조회 | 페이지네이션 (기본 20건, 최대 50건) |

### 분석 처리 방식

영상 분석은 수십 초가 소요되므로 동기 처리 시 요청 타임아웃이 발생한다.

```
POST /analysis            → 202 Accepted  { analysisId }
GET  /analysis/{id}/status → 폴링 (2초 주기)
GET  /analysis/{id}        → 결과 조회
POST /analysis/{id}/retry  → 실패 시 재시도 (최대 3회)
```

# 공통 형식 규칙

| 항목 | 규칙 |
| --- | --- |
| 날짜·시간 | ISO 8601 형식, KST 오프셋 포함 (`2026-08-06T14:30:00+09:00`) |

# 공통 오류 응답

모든 오류 응답은 아래 형식을 따른다.

| 필드 | 타입 | Null | 설명 |
| --- | --- | --- | --- |
| code | String | N | 오류 코드 |
| message | String | N | 사용자 표시용 메시지 (한국어) |
| field | String | Y | 오류가 발생한 필드 (검증 오류인 경우) |
| status | AnalysisStatus | Y | 현재 분석 상태 (상태 충돌인 경우) |

### 예시

```json
{
  "code": "ANIMAL_GROUP_UNSUPPORTED",
  "message": "현재 지원하지 않는 반려동물 그룹입니다.",
  "field": "animalGroup",
  "status": null
}
```

# 오류 코드

## 400 Bad Request

| code | 설명 |
| --- | --- |
| DEVICE_ID_REQUIRED | X-Device-Id 헤더가 없다 |
| DEVICE_ID_INVALID | UUID v4 형식이 아니다 |
| VIDEO_REQUIRED | 영상이 첨부되지 않았다 |
| VIDEO_FORMAT_INVALID | MP4(H.264)가 아니다 |
| VIDEO_DURATION_INVALID | 영상 길이가 3~30초 범위를 벗어났다 |
| ANIMAL_GROUP_REQUIRED | animalGroup이 없다 |
| ANIMAL_GROUP_UNSUPPORTED | 분석 기준이 정의되지 않은 그룹이다 |
| PAGE_INVALID | page가 1 미만이다 |
| SIZE_INVALID | size가 1~50 범위를 벗어났다 |
| STATUS_INVALID | 정의되지 않은 status 값이다 |

## 404 Not Found

| code | 설명 |
| --- | --- |
| ANALYSIS_NOT_FOUND | 분석이 존재하지 않거나 다른 기기의 분석이다 |

## 409 Conflict

| code | 설명 |
| --- | --- |
| ANALYSIS_IN_PROGRESS | 해당 기기에 진행 중인 분석이 있다 |
| ANALYSIS_NOT_COMPLETED | 분석이 완료되지 않아 결과를 반환할 수 없다 |
| ANALYSIS_NOT_DELETABLE | 진행 중인 분석은 삭제할 수 없다 |
| ANALYSIS_NOT_RETRYABLE | 실패한 분석만 재시도할 수 있다 |
| RETRY_LIMIT_EXCEEDED | 재시도 횟수를 초과했다 |

## 413 Payload Too Large

| code | 설명 |
| --- | --- |
| VIDEO_TOO_LARGE | 영상이 100MB를 초과했다 |

## 500 / 503

| code | Status | 설명 |
| --- | --- | --- |
| INTERNAL_ERROR | 500 | 서버 내부 오류 |
| QUEUE_FULL | 503 | 대기열이 가득 차 요청을 접수할 수 없다 |

> ※ `code` 는 클라이언트 분기 처리에, `message` 는 화면 표시에 사용한다.
> 
> ※ 서버 내부 오류 메시지를 `message` 에 그대로 노출하지 않는다.

# 공통 요청 헤더

MVP는 회원 기능을 제공하지 않으므로, 기기 식별자로 분석 이력을 분리한다.

| 헤더 | 필수 | 설명 |
| --- | --- | --- |
| X-Device-Id | O | 기기 식별자 (UUID v4) |

### 기기 식별자 규칙

| 항목 | 내용 |
| --- | --- |
| 생성 시점 | 앱 최초 실행 시 클라이언트가 생성한다. |
| 형식 | UUID v4 |
| 저장 위치 | 기기 로컬 저장소 |
| 전송 범위 | `/analysis` 로 시작하는 모든 요청 |
| 누락 시 | `400 Bad Request` 를 반환한다. |

### 소유권 검증

`analysisId` 로 접근하는 모든 API는 요청 헤더의 `X-Device-Id` 와 저장된 값이 일치하는지 확인한다.

| 상황 | 응답 |
| --- | --- |
| 일치 | 정상 처리 |
| 불일치 | `404 Not Found` |

> ※ 불일치 시 `403` 이 아니라 `404` 를 반환한다. `403` 은 해당 ID의 분석이 존재한다는 사실을 노출한다.

### 보안 한계

기기 식별자는 인증 수단이 아니다. 다음 한계를 전제로 사용한다.

| 항목 | 내용 |
| --- | --- |
| 기기 변경 | 이전 이력을 조회할 수 없다. |
| 앱 재설치 | 식별자가 초기화되어 이력이 유실된다. |
| 위조 | 헤더 값을 임의로 변경할 수 있다. UUID v4는 추측이 어렵지만 비밀값은 아니다. |

> ※ 회원 기능 도입 시 계정 기반 인증으로 전환한다.

## Enum : SpaceType

| 코드 | 이름 |
| --- | --- |
| living_room | 거실 |
| bedroom | 침실 |
| kitchen | 주방 |
| balcony | 베란다 |

공간에 따라 평가하는 분석 항목이 달라진다. 침실에서는 급식·급수 환경을, 주방에서는 휴식 공간을 평가하지 않는다.

> ※ 공간마다 평가 대상이 다르므로 서로 다른 공간의 점수를 직접 비교할 수 없다. 결과 화면에 공간 종류를 함께 표시한다.
> 
> ※ 공간별 적용 항목은 AI 분석 정의서를 따른다.

## Enum : RiskLevel

| 값 | 설명 | 마킹 색상 |
| --- | --- | --- |
| HIGH | 위험도 높음 | 빨간색 |
| MEDIUM | 위험도 보통 | 노란색 |
| LOW | 위험도 낮음 | 초록색 |
| SAFE | 위험 요소 아님 | 표시하지 않음 |

동일한 객체라도 반려동물 그룹에 따라 위험 수준이 달라진다. 창문은 고양이에게 `HIGH`, 소형견에게 `LOW` 이다.

다만 감전처럼 종에 무관한 위해는 최소 위험도를 보장한다. 전선은 모든 그룹에서 `HIGH` 이다.

> ※ `risk_level` 은 탐지 객체와 반려동물 그룹의 조합으로 백엔드가 판정한다. 판정 규칙은 AI 분석 정의서를 따른다.
> 
> ※ `risk_level` 은 마킹 색상 표시 전용이다. Pet Fit Score 산출에는 사용하지 않는다.

## Enum : AnalysisStatus

| 값 | 설명 |
| --- | --- |
| PENDING | 접수 완료, 처리 대기 |
| PROCESSING | 분석 진행 중 |
| COMPLETED | 분석 완료 |

> ※ 부분 성공은 정의하지 않는다. 어느 단계에서 실패하든 `FAILED` 로 처리한다.

---

## Enum : AnalysisStage

`status` 가 `PROCESSING` 인 동안의 세부 진행 단계이다.

**사용자에게 표시하기 위한 단계 구분이며, AI 파이프라인 12단계와 1:1로 대응하지 않는다.**

| 값 | 설명 | 포함하는 파이프라인 단계 |
| --- | --- | --- |
| FRAME_EXTRACTION | 프레임 추출 | 프레임 추출 |
| OBJECT_DETECTION | 객체 탐지 | 객체 탐지, 활동 공간 점유율 산출 |
| OBJECT_TRACKING | 객체 정리 | 객체 추적, 탐지 신뢰 기준 적용, 객체명 변환, 위험도 판정 |
| FRAME_SELECTION | 대표 프레임 선정 | 분석·객체 대표 프레임 선정 |
| RISK_MARKING | 위험 객체 마킹 | 마킹 이미지 생성 |
| SCORE_CALCULATION | Pet Fit Score 산출 | 점수 산출 |
| ENVIRONMENT_ANALYSIS | 환경 분석 | LLM/VLM 호출 |

### 단계를 묶는 이유

탐지 신뢰 기준 적용·객체명 변환·위험도 판정은 밀리초 단위로 끝나는 후처리다.

개별 단계로 노출하면 화면에 순식간에 스쳐 지나가고, **"객체명 변환 중"** 같은 문구는 사용자에게 의미가 없다.

파이프라인 정본은 AI 설계서이며, 본 Enum은 표시용 구분이다.

## Enum : RiskSource

| 값 | 설명 | 점수 반영 |
| --- | --- | --- |
| DETECTED | 객체 탐지 결과에 근거한 위험 요소 | ● |
| OBSERVED | 이미지에서 직접 확인한 위험 요소 | ○ |

`OBSERVED` 는 객체 탐지 대상 12종 밖의 위험 요소를 다룬다. 약병·화분·비닐봉지 등이 해당한다.

Pet Fit Score는 규칙 기반으로 산출되므로 `OBSERVED` 항목은 점수에 영향을 주지 않는다.

## Object : DetectedObject

| 필드 | 타입 | Null | 설명 |
| --- | --- | --- | --- |
| name | String | N | 객체 이름 |
| risk | RiskLevel | N | 위험 수준 |
| confidence | Float | N | 탐지 신뢰도 (0.0 ~ 1.0) |
| markedImage | String | Y | 마킹 이미지 경로 (위험 객체만, SAFE는 null) |

### 예시

```json
{
  "name": "전선",
  "risk": "HIGH",
  "confidence": 0.94,
  "markedImage": "/images/8f14e45f-ceea-467a-9c2b-1d3a7f6b90e1.jpg"
}
```

마킹 이미지는 **위험 객체마다 개별 생성**된다.

공간을 이동하며 촬영하므로 위험 요소가 서로 다른 장면에 나타난다. 각 이미지는 해당 객체가 가장 잘 보이는 프레임에 그 객체의 Bounding Box 하나만 표시한다.

| risk | markedImage |
| --- | --- |
| HIGH / MEDIUM / LOW | 이미지 경로 |
| SAFE | `null` |

### 동일 객체 다중 탐지

`detectedObjects` 는 **탐지된 인스턴스 단위**로 반환한다. 동일한 `name` 이 여러 번 나타날 수 있다.

전선이 두 곳에 있으면 두 항목으로 반환되며 각각 마킹 이미지를 가진다.

```json
[
  { "name": "전선", "risk": "HIGH", "markedImage": "/images/....jpg" },
  { "name": "전선", "risk": "HIGH", "markedImage": "/images/....jpg" },
  { "name": "의자", "risk": "SAFE", "markedImage": null }
]
```

### 정렬

동일 입력에 항상 동일한 순서로 반환한다.

| 순위 | 기준 | 방향 |
| --- | --- | --- |
| 1 | risk | HIGH → MEDIUM → LOW → SAFE |
| 2 | confidence | 내림차순 |
| 3 | name | 가나다순 |
| 4 | 내부 식별자 | 오름차순 |

`riskFactors` 는 `source` 가 `DETECTED` 인 항목이 먼저 오고, 같은 `source` 안에서는 생성 순서를 유지한다.

> ※ 목록 표시 시 `SAFE` 객체를 이름 기준으로 묶을지는 클라이언트가 결정한다.

## Object : Recommendation

| 필드 | 타입 | Null | 설명 |
| --- | --- | --- | --- |
| type | RecommendationType | N | 추천 유형 |
| text | String | N | 추천 내용 |
| priority | Integer | N | 추천 우선순위 (1부터 시작, 낮을수록 우선) |
| source | RiskSource | N | 판단 근거 |

### 예시

```json
{
  "type": "SAFETY",
  "text": "전선을 벽면으로 정리해주세요.",
  "priority": 1,
  "source": "DETECTED"
}
```

`source` 는 해당 추천의 근거가 된 위험 요소의 `source` 와 일치한다.

사용자가 실행해야 할 행동이므로, 확실한 탐지 결과에 근거한 것인지 이미지 관찰에 근거한 것인지 구분해 표시할 수 있어야 한다.

## Object : AnalysisSummary

분석 이력 목록에서 사용한다.

| 필드 | 타입 | Null | 설명 |
| --- | --- | --- | --- |
| analysisId | Integer(int64) | N | 분석 ID |
| animalGroup | AnimalGroup | N | 반려동물 그룹 |
| spaceType | SpaceType | N | 공간 종류 |
| status | AnalysisStatus | N | 분석 상태 |
| petFitScore | PetFitScore | Y | Pet Fit Score (COMPLETED일 때만) |
| thumbnailImage | String | Y | 대표 프레임 이미지 경로 (COMPLETED일 때만) |
| canRetry | Boolean | N | 재시도 가능 여부 |
| createdAt | String(ISO 8601) | N | 분석 요청 일시 |

이력 목록에 `FAILED` 항목이 함께 표시되므로, 목록에서 바로 재시도 버튼을 노출할 수 있도록 `canRetry` 를 포함한다.

| detectedObjects | DetectedObject[] | N | 탐지 객체 목록 (마킹 이미지 포함) |
| riskFactors | RiskFactor[] | N | 위험 요소 |
| analysis | String[] | N | AI 분석 결과 |
| recommendations | Recommendation[] | N | 환경 개선 추천 |
| createdAt | String(ISO 8601) | N | 분석 요청 일시 |
| completedAt | String(ISO 8601) | N | 분석 완료 일시 |

# API-002 영상 분석 요청

### Request

```
POST /analysis
Content-Type: multipart/form-data
X-Device-Id: 3f2b8c10-9d7e-4a51-8f6c-2e4b7a9d0c35
```

### Request Parameter

| Parameter | Type | Required | 설명 |
| --- | --- | --- | --- |
| video | File | O | 촬영 영상 |
| animalGroup | String | O | 반려동물 그룹 (AnimalGroup) |
| spaceType | String | O | 공간 종류 (SpaceType) |

### Validation

| 항목 | 조건 | 위반 시 |
| --- | --- | --- |
| X-Device-Id | 필수, UUID v4 형식 | 400 |
| video | 필수 | 400 |
| video 형식 | MP4 (H.264) | 400 |
| video 길이 | 3초 이상 30초 이하 | 400 |
| video 크기 | 100MB 이하 | 413 |
| animalGroup | 필수, 분석 가능 그룹만 허용 | 400 |
| spaceType | 필수, SpaceType 4개 값 | 400 |

### 업로드 제한

| 항목 | 값 |
| --- | --- |
| 최대 파일 크기 | 100MB |
| 허용 형식 | MP4 (H.264) |
| 영상 길이 | 3초 ~ 30초 |
| 권장 해상도 | 1920 × 1080 이하 |

권장 해상도를 초과하는 영상은 서버에서 축소 후 분석한다.

클라이언트는 업로드 전 해상도를 축소하여 전송 시간과 실패 가능성을 줄인다.

### 처리 제한

Mac Studio 단일 장비에서 객체 탐지와 LLM 추론을 수행하므로 동시 처리량을 제한한다.

| 항목 | 값 | 초과 시 |
| --- | --- | --- |
| 기기당 동시 분석 | 1건 | 409 |
| 서버 동시 처리 | 2건 | 대기열 등록 |
| 대기열 최대 | 10건 | 503 |

기기당 1건으로 제한하는 이유는, 한 기기가 연속 요청하여 대기열을 점유하는 것을 막기 위해서다.

대기열에 등록된 분석은 `PENDING` 상태를 유지한다.

### Response — 이미 진행 중인 분석이 있는 경우

```
HTTP/1.1 409 Conflict
```

```json
{
  "code": "ANALYSIS_IN_PROGRESS",
  "message": "이미 진행 중인 분석이 있습니다.",
  "field": null,
  "status": "PROCESSING"
}
```

### Request Example

```
video = room.mp4
animalGroup = small_dog
spaceType = living_room
```

### 처리 방식

영상 분석은 수십 초가 소요되므로 **비동기로 처리한다.**

요청을 접수하면 즉시 `analysisId` 를 반환하고, 분석은 백그라운드에서 수행한다.

클라이언트는 API-006으로 진행 상태를 조회하고, `COMPLETED` 가 되면 API-004로 결과를 조회한다.

### Response Type

| 필드 | 타입 | 설명 |
| --- | --- | --- |
| analysisId | Integer(int64) | 분석 ID |
| status | AnalysisStatus | 항상 `PENDING` |

### Response

```
HTTP/1.1 202 Accepted
```

```json
{
  "analysisId": 1,
  "status": "PENDING"
}
```

# API-006 분석 진행 상태 조회

### Request

```
GET /analysis/{analysisId}/status
X-Device-Id: 3f2b8c10-9d7e-4a51-8f6c-2e4b7a9d0c35
```

### Path Parameter

| Parameter | Type | Required | 설명 |
| --- | --- | --- | --- |
| analysisId | Integer(int64) | O | 분석 ID |

### Response Type

| 필드 | 타입 | Null | 설명 |
| --- | --- | --- | --- |
| analysisId | Integer(int64) | N | 분석 ID |
| status | AnalysisStatus | N | 분석 상태 |
| stage | AnalysisStage | Y | PROCESSING일 때 현재 단계, FAILED일 때 **실패한 단계** |
| progress | Integer | N | 진행률 (0 ~ 100) |
| retryCount | Integer | N | 지금까지 시도한 재시도 횟수 (0 ~ 3) |
| canRetry | Boolean | N | 재시도 가능 여부 |
| message | String | Y | 실패 사유 (FAILED일 때만) |

### canRetry

재시도 조건은 세 가지이며, 클라이언트가 각각을 판단하기 어렵다. 서버가 종합하여 불리언으로 제공한다.

```
canRetry = (status == FAILED) AND (retryCount < 3) AND (해당 기기에 진행 중인 분석 없음)
```

이 값이 없으면 클라이언트는 재시도를 눌러 `409` 를 받아야 불가능함을 알 수 있다. 실패를 예상하고 호출하는 구조가 된다.

### Response — 진행 중

```json
{
  "analysisId": 1,
  "status": "PROCESSING",
  "stage": "OBJECT_DETECTION",
  "progress": 20,
  "retryCount": 0,
  "canRetry": false,
  "message": null
}
```

### Response — 완료

```json
{
  "analysisId": 1,
  "status": "COMPLETED",
  "stage": null,
  "progress": 100,
  "retryCount": 0,
  "canRetry": false,
  "message": null
}
```

### Response — 실패

```json
{
  "analysisId": 1,
  "status": "FAILED",
  "stage": "OBJECT_DETECTION",
  "progress": 20,
  "retryCount": 1,
  "canRetry": true,
  "message": "객체 탐지에 실패했습니다."
}
```

### 실패 시 stage와 progress를 유지하는 이유

실패 지점을 구조화된 값으로 남긴다. `message` 의 자연어만으로는 클라이언트가 분기할 수 없다.

| 실패 단계 | 적절한 안내 |
| --- | --- |
| FRAME_EXTRACTION · OBJECT_DETECTION | 영상 품질 문제일 가능성이 높다. **재촬영**을 권한다 |
| SCORE_CALCULATION · ENVIRONMENT_ANALYSIS | 서버 측 일시 오류일 가능성이 높다. **재시도**를 권한다 |

`progress` 를 0으로 되돌리면 10에서 실패한 것과 82까지 진행하다 실패한 것이 구분되지 않는다.

### 단계별 진행률

`progress` 는 단계 진입 시점의 값이다.

| stage | progress | 구간 폭 |
| --- | --- | --- |
| (PENDING) | 0 | |
| FRAME_EXTRACTION | 10 | 10 |
| OBJECT_DETECTION | 20 | **35** |
| OBJECT_TRACKING | 55 | 10 |
| FRAME_SELECTION | 65 | 7 |
| RISK_MARKING | 72 | 6 |
| SCORE_CALCULATION | 78 | 4 |
| ENVIRONMENT_ANALYSIS | 82 | **18** |
| (COMPLETED) | 100 | |

객체 탐지와 환경 분석이 전체 시간의 대부분을 차지하므로 해당 구간에 넓은 범위를 배정한다.

`OBJECT_TRACKING` 구간(55 → 65)에는 객체 추적 외에 탐지 신뢰 기준 적용·객체명 변환·위험도 판정이 함께 포함된다. 모두 짧은 후처리이므로 하나의 구간으로 묶는다.

> ※ 구간 내 진행률은 선형으로 보간하지 않는다. 단계 진입 시점에만 값을 갱신한다.

### 폴링 권장 간격

| 항목 | 값 |
| --- | --- |
| 폴링 주기 | 2초 |
| 클라이언트 최대 대기 시간 | 180초 |
| 서버 처리 제한 시간 | 180초 |
| 초과 시 처리 | 서버가 `FAILED` 로 전환하고, 클라이언트는 재촬영을 안내한다. |

> ※ 서버도 동일한 제한 시간을 적용한다. 서버 타임아웃이 없으면 중단된 분석이 `PROCESSING` 으로 영구히 남아 삭제할 수 없게 된다.

# API-007 실패한 분석 재시도

### Request

```
POST /analysis/{analysisId}/retry
X-Device-Id: 3f2b8c10-9d7e-4a51-8f6c-2e4b7a9d0c35
```

**이미 업로드된 영상을 그대로 사용하여 분석을 다시 수행한다.** 영상을 재전송하지 않는다.

LLM 호출 실패, 일시적 서버 오류 등 영상 자체와 무관한 실패에 대응한다.

### Path Parameter

| Parameter | Type | Required | 설명 |
| --- | --- | --- | --- |
| analysisId | Integer(int64) | O | 분석 ID |

### 재시도 조건

| 조건 | 위반 시 |
| --- | --- |
| `status` 가 `FAILED` | 409 `ANALYSIS_NOT_RETRYABLE` |
| `retryCount` 가 3 미만 | 409 `RETRY_LIMIT_EXCEEDED` |
| 해당 기기에 진행 중인 분석 없음 | 409 `ANALYSIS_IN_PROGRESS` |
| 대기열 여유 있음 | 503 `QUEUE_FULL` |

### 처리 방식

기존 `analysisId` 를 그대로 사용한다. 새 분석을 생성하지 않는다.

| 항목 | 처리 |
| --- | --- |
| status | `FAILED` → `PENDING` |
| retryCount | 1 증가 |
| errorMessage | `null` 로 초기화 |
| 탐지 객체 · 추천 | 행 삭제 후 재생성 |
| 대표 프레임 · 마킹 이미지 | **파일 삭제 후 재생성** |
| 업로드 영상 | **유지** (재분석 입력) |

새 ID를 만들지 않는 이유는, 동일한 영상에 대한 실패 기록이 이력에 중복으로 쌓이는 것을 막기 위해서다.

### 기존 파일 삭제

파일명은 UUID이므로 재생성 시 **새 이름이 부여된다.** 기존 파일을 삭제하지 않으면 DB 참조가 끊긴 채 디스크에 잔류하고, 경로를 잃어 이후 추적할 수 없다.

| 순서 | 처리 |
| --- | --- |
| 1 | 기존 이미지 경로를 조회한다 |
| 2 | 파일을 삭제한다 |
| 3 | 자식 행을 삭제하고 컬럼을 초기화한다 |

경로 조회 전에 행을 삭제하면 파일을 찾을 수 없다. 상세 절차는 DB 명세서의 파일 생명주기를 따른다.

> ※ 정리하지 않으면 3회 재시도 시 분석 1건당 최대 12장의 미사용 이미지가 누적된다.

### Response

```
HTTP/1.1 202 Accepted
```

```json
{
  "analysisId": 1,
  "status": "PENDING",
  "retryCount": 1
}
```

### Response — 재시도 불가

```
HTTP/1.1 409 Conflict
```

```json
{
  "code": "ANALYSIS_NOT_RETRYABLE",
  "message": "실패한 분석만 다시 시도할 수 있습니다.",
  "field": null,
  "status": "COMPLETED"
}
```

### 재시도 횟수 제한

| 항목 | 값 |
| --- | --- |
| 최대 재시도 횟수 | 3회 |
| 초과 시 안내 | 재촬영을 안내한다 |

영상 자체에 문제가 있으면 재시도해도 계속 실패하므로 횟수를 제한한다.

# API-005 분석 결과 삭제

### Request

```
DELETE /analysis/{analysisId}
X-Device-Id: 3f2b8c10-9d7e-4a51-8f6c-2e4b7a9d0c35
```

분석 결과와 함께 업로드된 영상·생성된 이미지 파일을 모두 삭제한다.

### 삭제 순서

| 순서 | 처리 |
| --- | --- |
| 1 | 영상·대표 프레임·마킹 이미지 경로를 모두 조회한다 |
| 2 | 파일을 삭제한다 |
| 3 | `analysis` 행을 삭제한다 (자식 행은 CASCADE로 연쇄 삭제) |

DB 행을 먼저 삭제하면 파일 경로를 잃어 영구히 추적할 수 없으므로, 파일을 먼저 삭제한다.

### 삭제 가능 조건

| status | 삭제 |
| --- | --- |
| COMPLETED | 가능 |
| FAILED | 가능 |
| PENDING | **불가 (409)** |
| PROCESSING | **불가 (409)** |

진행 중인 분석을 삭제하면 백그라운드 작업이 삭제된 레코드를 갱신하려 시도하고, 쓰기 중인 파일이 남는다.

`PROCESSING` 은 서버 처리 제한 시간(180초)을 초과하면 `FAILED` 로 전환되므로 이후 삭제할 수 있다.

### Path Parameter

| Parameter | Type | Required | 설명 |
| --- | --- | --- | --- |
| analysisId | Integer(int64) | O | 분석 ID |

### Response Type

| 필드 | 타입 | 설명 |
| --- | --- | --- |
| message | String | 처리 결과 메시지 |

### Response

```json
{
  "message": "분석 결과가 삭제되었습니다."
}
```

### Response — 진행 중인 분석

```
HTTP/1.1 409 Conflict
```

```json
{
  "code": "ANALYSIS_NOT_DELETABLE",
  "message": "분석이 진행 중이어서 삭제할 수 없습니다.",
  "field": null,
  "status": "PROCESSING"
}
```

# 공통 HTTP 응답 코드

| Status Code | 설명 |
| --- | --- |
| 200 | 요청 성공 |
| 201 | 생성 성공 |
| 202 | 요청 접수 완료 (비동기 처리 시작) |
| 400 | 잘못된 요청 (X-Device-Id 누락 포함) |
| 404 | 데이터 없음 (다른 기기의 분석에 접근한 경우 포함) |
| 409 | 현재 상태에서 처리할 수 없는 요청 (분석 미완료, 진행 중 분석 존재, 진행 중 삭제) |
| 413 | 업로드 파일 크기 초과 |
| 500 | 서버 오류 |
| 503 | 대기열 초과로 요청을 처리할 수 없음 |

```

        │
        ▼

        │                        │                              │
        ▼                        │  GET /analysis/{id}/status   │

                                 │            │                 │
   프레임 추출                    │            ▼                 │
   객체 탐지·추적                 │  status = PROCESSING         │

        │
        ▼
status = COMPLETED
        │
        ▼
GET /analysis/{id}  ──────────▶ 200 OK { AnalysisDetail }
```
