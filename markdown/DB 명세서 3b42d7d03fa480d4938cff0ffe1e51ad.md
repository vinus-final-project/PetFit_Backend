# DB 명세서

# 문서 개요

본 문서는 Pet Fit 서비스에서 사용하는 데이터베이스 테이블 및 컬럼의 상세 정보를 정의한다.

영상 기반 AI 분석 시스템에서 생성되는 분석 결과, 객체 탐지 결과 및 환경 개선 추천 데이터를 저장하기 위한 테이블 명세를 제공한다.

### 시각 저장 방식

MySQL에는 타임존을 보존하는 타입이 없다. 두 후보의 특성은 다음과 같다.

| 타입 | 동작 | 문제 |
| --- | --- | --- |
| TIMESTAMP | UTC 저장 후 세션 타임존으로 변환 | **2038년 상한** |
| **DATETIME(6)** | 저장한 값을 그대로 보관 | 변환을 애플리케이션이 담당 |

`DATETIME(6)` 에 **KST(UTC+9)** 로 저장하고, API 응답 시 오프셋 `+09:00` 을 붙여 반환한다. 2038년 상한이 없다.

#### KST로 저장하는 이유

| 항목 | 내용 |
| --- | --- |
| 서머타임 없음 | 한국은 DST를 시행하지 않는다. 로컬 시간 저장의 고전적 문제인 **중복되는 시각**과 **존재하지 않는 시각**이 발생하지 않는다 |
| 운영 편의 | DB를 직접 조회했을 때 사용자가 화면에서 본 시각과 같은 값이 나온다. 장애 대응 시 암산 변환이 필요 없다 |
| 서비스 범위 | MVP는 국내 전용이다. 해외 확장 시 UTC 전환 마이그레이션을 검토한다 |

#### 세션 타임존을 반드시 고정한다

`created_at` 의 기본값 `CURRENT_TIMESTAMP(6)` 는 **세션 타임존을 따른다.** 고정하지 않으면 서버 OS 설정에 따라 값이 달라진다.

```sql
SET time_zone = '+09:00'
```

애플리케이션은 커넥션 풀이 새 연결을 만들 때마다 위 명령을 실행한다. 개발 장비와 배포 서버의 타임존이 달라도 같은 값이 저장된다.

확인 방법은 다음과 같다.

```sql
SELECT @@session.time_zone, NOW(6);
```

> ※ 고정을 누락하면 서버가 KST면 정상, UTC면 9시간 이른 값이 저장된다. **오류가 나지 않고 조용히 틀린다.**

### 상태 전이

```
        ┌──────────────────────────────────┐
        │      재시도 (retry_count < 3)     │
        ▼                                  │
   ┌─────────┐      ┌────────────┐      ┌────────┐
   │ PENDING │─────▶│ PROCESSING │─────▶│ FAILED │
   └─────────┘      └──────┬─────┘      └────────┘
                           │
                           ▼
                    ┌───────────┐
                    │ COMPLETED │
                    └───────────┘
```

`FAILED` 에서 재시도하면 `PENDING` 으로 되돌아가며 `retry_count` 가 1 증가한다.

새 레코드를 생성하지 않으므로 동일 영상의 실패 기록이 이력에 중복되지 않는다.

`COMPLETED` 는 종료 상태이며 다른 상태로 전이하지 않는다.

| 상태 | 채워지는 값 |
| --- | --- |
| PENDING | device_id, animal_group, space_type, video_path, created_at |
| PROCESSING | stage, progress |
| COMPLETED | capture_duration, frame_count, occupancy_ratio, thumbnail_path, 점수 5종, risk_factors, analysis_result, completed_at |
| FAILED | error_message, stage · progress 유지 (실패 지점 보존) |

> ※ 이미지 경로와 점수는 분석 완료 전에는 값이 없으므로 NULL 또는 기본값을 유지한다.
> 
> ※ 부분 성공은 정의하지 않는다. 어느 단계에서 실패하든 FAILED로 처리한다.

### 컬럼 정의

| 컬럼명 | 타입 | PK | FK | NULL | 기본값 | 설명 |
| --- | --- | --- | --- | --- | --- | --- |
| object_id | BIGINT | ● |  | N | AUTO_INCREMENT | 객체 ID |
| analysis_id | BIGINT |  | ● | N | - | analysis 참조 |
| object_name | VARCHAR(50) |  |  | N | - | 객체 이름 |
| confidence | DECIMAL(5,4) |  |  | N | - | 탐지 신뢰도 (프레임 중 최댓값) |
| detection_frame_count | INT |  |  | N | - | 해당 객체가 탐지된 프레임 수 |
| risk_level | VARCHAR(20) |  |  | N | SAFE | 위험 수준(HIGH/MEDIUM/LOW/SAFE) |
| frame_number | INT |  |  | N | - | 객체 대표 프레임 번호 |
| marked_image_path | VARCHAR(255) |  |  | Y | NULL | 마킹 이미지 경로 (위험 객체만 생성) |
| x | DECIMAL(5,4) |  |  | N | - | Bounding Box X (정규화 0.0 ~ 1.0) |
| y | DECIMAL(5,4) |  |  | N | - | Bounding Box Y (정규화 0.0 ~ 1.0) |
| width | DECIMAL(5,4) |  |  | N | - | Bounding Box Width (정규화 0.0 ~ 1.0) |
| height | DECIMAL(5,4) |  |  | N | - | Bounding Box Height (정규화 0.0 ~ 1.0) |

본 테이블은 기본값을 두지 않는다. CHECK 제약이 `detection_frame_count >= 1`, `frame_number >= 1`, `width > 0` 을 요구하므로 **0은 존재할 수 없는 값**이다.

행은 분석이 완료된 뒤 전체 값을 갖추어 INSERT하므로 기본값이 필요하지 않다.

### 저장 단위

**탐지된 객체 인스턴스마다 1행을 저장한다.**

동일 클래스가 여러 개 탐지되면 각각 별도 행으로 저장한다.

| 상황 | 저장 |
| --- | --- |
| 의자 3개 탐지 | 3행 |
| 전선 2개 탐지 | 2행 (각각 마킹 이미지 생성) |

위험 객체는 개별 위치를 표시해야 하므로 인스턴스 단위 저장이 필요하다. 전선이 두 곳에 있으면 두 곳 모두 보여야 한다.

> ※ 활동 공간 점유율은 프레임 단위로 계산되어 `analysis.occupancy_ratio` 에 저장되므로, 본 테이블의 저장 단위와 무관하다.
> 
> ※ 감점 규칙은 객체의 존재 여부만 사용하므로 인스턴스 수는 점수에 영향을 주지 않는다.

### 저장 대상

탐지 신뢰 기준을 통과한 객체만 저장한다.

| 조건 | 값 |
| --- | --- |
| confidence | 0.40 이상 |
| detection_frame_count | 2 이상 |

기준 미달 객체는 오탐으로 간주하여 저장하지 않는다. 판정 규칙은 AI 분석 정의서를 따른다.

### 객체 대표 프레임

`frame_number` 는 해당 객체가 가장 잘 보이는 프레임 번호이다. **객체마다 다를 수 있다.**

공간을 이동하며 촬영하므로 위험 요소가 서로 다른 장면에 나타난다. 객체별로 프레임을 선정해야 모든 위험 요소를 표시할 수 있다.

| object_name | frame_number |
| --- | --- |
| 전선 | 3 |
| 창문 | 18 |
| 계단 | 25 |

> ※ 분석 대표 프레임은 이미지 경로(`analysis.thumbnail_path`)로만 저장하며 프레임 번호는 보관하지 않는다. 본 컬럼은 객체별 대표 프레임 번호로 용도가 다르다.

### 마킹 이미지

| risk_level | marked_image_path |
| --- | --- |
| HIGH / MEDIUM / LOW | 생성 후 경로 저장 |
| SAFE | NULL |

객체 1개당 이미지 1장을 생성하며, 해당 객체의 Bounding Box 1개만 표시한다.

### 좌표 기준

Bounding Box 좌표는 **해당 객체의 객체 대표 프레임** 가로·세로 길이를 각각 1.0으로 하는 정규화 좌표로 저장한다.

| 항목 | 내용 |
| --- | --- |
| 원점 | 프레임 좌측 상단 |
| 범위 | 0.0 이상 1.0 이하 |
| 기준 프레임 | `frame_number` 가 가리키는 프레임 |
| 화면 표시 | `표시 좌표 = 정규화 좌표 × 표시 크기` |

해상도와 무관하게 유효하므로 이미지 리사이즈 시에도 좌표가 어긋나지 않는다.

### 보관 사유

좌표는 마킹 이미지 생성 시점에만 사용되며, **현재 API 응답에는 포함되지 않는다.**

그럼에도 보관하는 이유는 다음과 같다.

| 용도 | 내용 |
| --- | --- |
| 결과 화면 확장 | 썸네일에서 위험 요소를 선택하는 인터랙션의 전제 데이터 |
| 오류 추적 | 마킹 위치가 잘못된 경우 원인을 이미지가 아닌 데이터로 확인 |
| 재마킹 | 마킹 표현 방식 변경 시 이미지를 다시 생성할 수 있다 |

> ※ 사용처가 없어 보이더라도 제거하지 않는다. 위 용도를 위해 의도적으로 보관하는 컬럼이다.

> ※ 객체마다 기준 프레임이 다르므로 서로 다른 객체의 좌표를 한 이미지에 함께 그리지 않는다.

### 삭제 동작

`analysis` 삭제 시 자식 행을 연쇄 삭제한다.

MySQL의 외래키 기본 동작은 `RESTRICT` 이므로, 명시하지 않으면 **자식 행이 존재할 때 부모 삭제가 거부된다.** 분석 결과 삭제 API가 외래키 위반으로 실패한다.

외래키는 `InnoDB` 엔진에서만 동작한다. `MyISAM` 은 구문을 무시한다.

```sql
FOREIGN KEY (analysis_id) REFERENCES analysis(analysis_id) ON DELETE CASCADE
```

> ※ 연쇄 삭제는 DB 행만 제거한다. 파일은 별도로 삭제해야 한다. 아래 파일 생명주기를 따른다.

# 데이터 무결성

| 항목 | 내용 |
| --- | --- |
| Primary Key | 각 테이블의 PK는 중복을 허용하지 않는다. |
| Foreign Key | analysis_id는 analysis.analysis_id를 참조한다. |
| NOT NULL | 필수 컬럼은 NULL을 허용하지 않는다. |
| Timestamp | created_at은 생성 시 자동 저장한다. 값은 KST이며 표시 시 오프셋만 붙인다. |
| JSON | analysis_result는 String 배열, risk_factors는 `{text, source}` 객체 배열을 저장한다. 기본값은 빈 배열이다. |
| RiskSource | risk_factors[].source는 DETECTED 또는 OBSERVED만 허용한다. |
| 정규화 좌표 | Bounding Box 좌표는 0.0 이상 1.0 이하만 허용한다. |
| CHECK | 열거형 컬럼과 범위가 정해진 수치 컬럼은 CHECK 제약으로 검증한다. |
| 소유권 | 분석 조회·삭제는 device_id가 일치하는 경우에만 허용한다. |
| 파일명 | 영상·이미지 파일명은 UUID를 사용한다. 순차 번호를 사용하지 않는다. |
| 삭제 조건 | status가 COMPLETED 또는 FAILED인 경우에만 삭제한다. |
| 처리 제한 시간 | PROCESSING이 180초를 초과하면 FAILED로 전환한다. |

# DDL 작성 규칙

| 항목 | 규칙 |
| --- | --- |
| DBMS | MySQL 8.0 |
| PK 자동 생성 | `AUTO_INCREMENT` 를 사용한다. |
| 날짜·시간 | `DATETIME(6)` 에 **KST** 로 저장한다. 세션 타임존을 `+09:00` 으로 고정한다. |
| 배열 저장 | `JSON` 을 사용한다. |
| 열거형 | `VARCHAR` + `CHECK` 제약을 사용한다. |
| 외래키 | `ON DELETE CASCADE` 를 명시한다. |
| 소수 | `FLOAT`·`DOUBLE` 을 사용하지 않고 `DECIMAL` 을 사용한다. |
| 문자셋 | `utf8mb4` / `utf8mb4_unicode_ci` 를 사용한다. |
| 스토리지 엔진 | `InnoDB` 를 사용한다. 외래키와 트랜잭션이 필요하다. |

`FLOAT`·`DOUBLE` 은 이진 부동소수점이라 저장·조회 과정에서 미세 오차가 발생한다. `confidence` 는 정렬 기준이고 `occupancy_ratio` 와 좌표는 임계값 비교에 사용되므로, 오차가 순서와 판정을 바꿀 수 있다.

`DECIMAL(5,4)` 은 십진 고정소수점이라 저장한 값이 그대로 보존된다. 소수점 4자리 비교 규칙과도 자릿수가 일치한다.

`utf8mb4` 를 쓰는 이유는 MySQL의 `utf8` 이 3바이트까지만 지원하는 불완전한 UTF-8이기 때문이다. 4바이트 문자를 저장할 수 없다.

`ENUM` 타입 대신 `VARCHAR` + `CHECK` 를 사용하는 이유는, MySQL의 `ENUM` 은 값을 추가·삭제할 때 `ALTER TABLE` 로 컬럼 정의 전체를 다시 써야 하고 정렬 순서가 선언 순서에 묶이기 때문이다. 반려동물 그룹처럼 확장이 예정된 값에는 `CHECK` 가 적합하다.

> ※ `CHECK` 제약은 **MySQL 8.0.16 이상**에서만 동작한다. 그 미만 버전은 구문을 파싱만 하고 무시하므로 제약이 걸리지 않는다. `SELECT VERSION();` 으로 확인한다.

> ※ 테이블명과 컬럼명은 소문자 snake_case로 통일한다. MySQL의 테이블명 대소문자 구분은 OS와 `lower_case_table_names` 설정에 따라 달라져, 대문자가 섞이면 Windows에서 개발하고 Linux에 배포할 때 테이블을 찾지 못한다.

# CHECK 제약 조건

값이 정해진 컬럼은 CHECK 제약으로 무결성을 보장한다.

제약이 없으면 `PROCESING` 같은 오타가 그대로 저장되고, 해당 행은 어떤 상태 필터에도 잡히지 않는다. 진행 중 분석 검사도 통과하여 동시 실행 제한이 무력화된다.

## analysis

| 컬럼 | 제약 |
| --- | --- |
| device_id | UUID v4 형식 (`^[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$`) |
| status | `IN ('PENDING','PROCESSING','COMPLETED','FAILED')` |
| stage | `IS NULL OR IN ('FRAME_EXTRACTION','OBJECT_DETECTION','OBJECT_TRACKING','FRAME_SELECTION','RISK_MARKING','SCORE_CALCULATION','ENVIRONMENT_ANALYSIS')` |
| animal_group | `IN ('small_dog','large_dog','cat')` |
| space_type | `IN ('living_room','bedroom','kitchen','balcony')` |
| progress | `BETWEEN 0 AND 100` |
| retry_count | `BETWEEN 0 AND 3` |
| total_score | `BETWEEN 0 AND 100` |
| safety_score | `BETWEEN 0 AND 100` |
| activity_score | `BETWEEN 0 AND 100` |
| rest_score | `BETWEEN 0 AND 100` |
| environment_score | `BETWEEN 0 AND 100` |
| occupancy_ratio | `BETWEEN 0 AND 1` |
| capture_duration | `= 0 OR BETWEEN 3 AND 30` |
| frame_count | `= 0 OR BETWEEN 15 AND 30` |

`capture_duration` 과 `frame_count` 가 0을 허용하는 이유는 `PENDING` 상태에서 아직 영상을 분석하지 않았기 때문이다.

**0을 허용하지 않으면 접수 시점의 INSERT가 CHECK 위반으로 실패한다.** 기본값이 CHECK 범위 밖이면 해당 컬럼 없이 INSERT할 수 없다.

`capture_duration` 과 `frame_count` 는 API로 반환하지 않는다. AI 성능 평가서의 `평균 영상 길이` · `평균 프레임 수` 측정에 사용한다.

### 복합 제약

| 제약 | 내용 |
| --- | --- |
| stage 정합성 | `status` 가 `PROCESSING` 이면 반드시 값을 가진다. `FAILED` 는 **실패한 단계를 보존한다.** `PENDING` · `COMPLETED` 는 NULL이다 |
| progress 정합성 | `PENDING` 은 0, `COMPLETED` 는 100이다. `PROCESSING` · `FAILED` 는 단계별 값을 가진다 |
| completed_at 정합성 | `completed_at` 은 `status = 'COMPLETED'` 인 경우에만 값을 가진다 |
| error_message 정합성 | `error_message` 는 `status = 'FAILED'` 인 경우에만 값을 가진다 |

```sql
CHECK ((status = 'PROCESSING' AND stage IS NOT NULL)
    OR (status = 'FAILED')
    OR (status IN ('PENDING','COMPLETED') AND stage IS NULL))

CHECK ((status = 'PENDING'   AND progress = 0)
    OR (status = 'COMPLETED' AND progress = 100)
    OR (status IN ('PROCESSING','FAILED')))
```

#### FAILED가 stage를 유지하는 이유

API 명세서 API-006은 실패 응답에 **실패한 단계**를 포함한다. 실패 지점에 따라 클라이언트가 안내할 내용이 달라지기 때문이다.

| 실패 단계 | 안내 |
| --- | --- |
| FRAME_EXTRACTION · OBJECT_DETECTION | 영상 품질 문제. **재촬영** |
| SCORE_CALCULATION · ENVIRONMENT_ANALYSIS | 서버 일시 오류. **재시도** |

`stage` 를 NULL로 강제하면 이 분기가 불가능해진다. 다만 대기열 초과처럼 파이프라인 진입 전에 실패하면 `stage` 는 NULL이다.

#### progress 단계별 수치를 CHECK에 넣지 않는 이유

`progress` 는 `stage` 에서 파생되는 값이며 매핑은 1:1이다. 엄밀히는 이행적 종속(3NF 위반)이다.

단계별 수치(10 · 20 · 55 · 65 · 72 · 78 · 82)를 CHECK에 넣으면 정합성이 강제되지만, 값을 조정할 때마다 스키마 마이그레이션이 발생한다. 이 수치는 사용자 체감에 맞춰 조정되는 표시용 값이다.

따라서 **변하지 않는 경계값만 CHECK로 강제하고**, 단계별 매핑은 애플리케이션의 `AnalysisStage.progress` 를 유일한 정본으로 둔다. 저장·응답 양쪽이 `progress_for(status, stage)` 를 거치므로 두 값이 어긋나지 않는다.

## 애플리케이션에서 검증하는 항목

성능평가로 조정되는 값은 CHECK 제약에 넣지 않는다. 값이 바뀔 때마다 스키마 마이그레이션이 발생하기 때문이다.

| 항목 | 현재 값 | 검증 위치 |
| --- | --- | --- |
| 객체 채택 confidence 임계값 | 0.40 이상 | 애플리케이션 |
| 최소 탐지 프레임 수 | 2 이상 | 애플리케이션 |
| 활동 공간 점유율 임계값 | 0.40 / 0.60 / 0.75 | 애플리케이션 |
| 프레임 추출 간격 | 초당 3프레임 | 애플리케이션 |
| object_name 허용 값 | 탐지 대상 12종 | 애플리케이션 |

`object_name` 은 열거형에 가깝지만 CHECK 제약을 걸지 않는다. **최종 탐지 객체가 성능평가로 확정되기 때문이다.** 클래스가 추가·제외될 때마다 스키마 마이그레이션이 발생한다.

대신 객체 코드 매핑표에 없는 값은 백엔드에서 저장하지 않는다.

**CHECK 제약은 변하지 않는 불변식에만 사용한다.** 열거형 값과 0~1 범위 같은 것이 해당한다.

# 파일 생명주기

파일은 데이터베이스 트랜잭션에 포함되지 않으므로 생성·삭제 시점을 명시한다.

| 파일 | 저장 컬럼 | 생성 시점 | 삭제 시점 |
| --- | --- | --- | --- |
| 업로드 영상 | `analysis.video_path` | 분석 요청 | 분석 삭제 |
| 분석 대표 프레임 | `analysis.thumbnail_path` | 분석 완료 | 분석 삭제, **재시도** |
| 객체 마킹 이미지 | `detected_object.marked_image_path` | 분석 완료 | 분석 삭제, **재시도** |

영상은 재시도에 사용하므로 재시도 시 삭제하지 않는다.

---

## 분석 삭제 절차

순서를 지키지 않으면 파일 경로를 잃어 고아 파일이 발생한다.

| 순서 | 처리 |
| --- | --- |
| 1 | 삭제 대상의 파일 경로를 모두 조회한다 |
| 2 | 파일을 삭제한다 |
| 3 | `analysis` 행을 삭제한다 (자식 행은 연쇄 삭제) |

파일을 먼저 삭제하는 이유는, DB 행을 먼저 지우면 **경로를 알 수 없어 파일을 영구히 추적할 수 없기 때문이다.**

| 실패 지점 | 결과 | 대응 |
| --- | --- | --- |
| 2단계 실패 | DB·파일 모두 유지 | 삭제 실패로 응답. 재시도 가능 |
| 3단계 실패 | 파일만 삭제됨 | DB 행이 남아 이미지가 깨진 상태로 조회됨 |

3단계 실패는 파일 삭제를 되돌릴 수 없으므로, 해당 분석을 `FAILED` 로 전환하여 결과 조회를 차단한다.

---

## 재시도 시 파일 처리

재시도는 기존 `analysisId` 를 재사용하지만 **파일은 새 UUID로 생성된다.**

기존 파일을 삭제하지 않으면 DB에서 참조가 끊긴 채 디스크에 잔류한다. 경로를 잃어 이후 추적도 불가능하다.

| 순서 | 처리 |
| --- | --- |
| 1 | `thumbnail_path` 와 자식 행의 `marked_image_path` 를 조회한다 |
| 2 | 조회한 파일을 삭제한다 |
| 3 | `detected_object` · `recommendation` 행을 삭제한다 |
| 4 | `thumbnail_path` 를 `NULL` 로, 점수·배열 컬럼을 기본값으로 초기화한다 |
| 5 | `status` 를 `PENDING` 으로, `retry_count` 를 1 증가시킨다 |

`video_path` 는 유지한다. 재분석의 입력이다.

> ※ 최대 3회 재시도 시 파일을 정리하지 않으면 분석 1건당 최대 12장의 미사용 이미지가 누적된다.

# 데이터 저장 흐름

단계별로 어느 테이블·컬럼이 채워지는지를 나타낸다.

```
분석 요청 접수
      │
      ▼
analysis INSERT
  device_id, animal_group, video_path, status=PENDING
      │
      ▼
[ AI 분석 파이프라인 ]
      │
      ▼
analysis UPDATE
  status=PROCESSING, stage, progress
      │
      ▼
analysis UPDATE
  capture_duration, frame_count, occupancy_ratio
  thumbnail_path, 점수 5종
      │
      ├──────────────────┐
      ▼                  ▼
detected_object      recommendation
  INSERT               INSERT
      │                  │
      └────────┬─────────┘
               ▼
        analysis UPDATE
  risk_factors, analysis_result
  status=COMPLETED, completed_at
```

> ※ AI 분석 파이프라인의 내부 단계는 **AI 설계서**를 따른다.
