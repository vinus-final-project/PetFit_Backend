# DB 설계서

# 문서 개요

본 문서는 Pet Fit 서비스의 데이터베이스 구조를 정의한다.

사용자가 촬영한 영상과 AI 분석 결과를 저장하기 위한 데이터베이스 구조를 설계하며, 영상 기반 객체 탐지 및 환경 분석 결과를 효율적으로 관리할 수 있도록 구성한다.

# 테이블 관계

| 부모 | 자식 | 관계 | 삭제 동작 |
| --- | --- | --- | --- |
| analysis | detected_object | 1 : N | ON DELETE CASCADE |
| analysis | recommendation | 1 : N | ON DELETE CASCADE |

```sql
FOREIGN KEY (analysis_id) REFERENCES analysis(analysis_id) ON DELETE CASCADE
```

> ※ MySQL 외래키 기본 동작은 `RESTRICT` 이다. 명시하지 않으면 자식 행이 있을 때 부모 삭제가 거부된다.
> 
> ※ 외래키는 `InnoDB` 에서만 동작한다. 스토리지 엔진을 반드시 지정한다.
> 
> ※ 연쇄 삭제는 DB 행만 제거한다. 파일 삭제 절차는 DB 명세서를 따른다.

# 테이블 개요

컬럼별 타입·NULL 여부·기본값·제약은 **DB 명세서**를 따른다. 본 문서는 구조와 관계를 정의한다.

## analysis

영상 기반 AI 분석 결과를 저장하는 메인 테이블

| 항목 | 내용 |
| --- | --- |
| 역할 | 분석 1건의 상태·점수·서술 결과를 보관한다 |
| 컬럼 구성 | 식별(2) · 입력(3) · 상태(5) · 산출(8) · 서술(2) · 시각(2) |
| 분석 조건 | `animal_group` 과 `space_type` 조합에 따라 평가 항목이 달라진다 |
| 생명주기 | 요청 시 생성, 파이프라인 진행에 따라 갱신 |

### 상태 전이

```
        ┌──────────────────────────────────┐
        │      재시도 (최대 3회)             │
        ▼                                  │
   ┌─────────┐      ┌────────────┐      ┌────────┐
   │ PENDING │─────▶│ PROCESSING │─────▶│ FAILED │
   └─────────┘      └──────┬─────┘      └────────┘
                           │
                           ▼
                    ┌───────────┐
                    │ COMPLETED │
                    └───────────┘
```

> ※ 이미지 경로와 점수는 분석 완료 전에는 값이 없다.
> 
> ※ 부분 성공은 정의하지 않는다. 어느 단계에서 실패하든 FAILED로 처리한다.

---

## detected_object

탐지된 객체 정보를 저장하는 테이블

| 항목 | 내용 |
| --- | --- |
| 역할 | 탐지 신뢰 기준을 통과한 객체를 인스턴스 단위로 보관한다 |
| 저장 단위 | 객체 인스턴스 1개당 1행 |
| 좌표 기준 | 해당 객체의 `frame_number` 프레임 기준 정규화 좌표 |

> ※ `frame_number` 는 객체마다 다를 수 있다. 객체별로 가장 잘 보이는 프레임을 선정한다.
> 
> ※ 마킹 이미지는 객체 1개당 1장이며 `SAFE` 객체는 생성하지 않는다.

---

## recommendation

환경 개선 추천을 저장하는 테이블

| 항목 | 내용 |
| --- | --- |
| 역할 | LLM이 생성한 개선 추천을 유형·우선순위와 함께 보관한다 |
| 저장 단위 | 추천 1건당 1행 |
| 정렬 | `priority` 오름차순 |

> ※ `UNIQUE (analysis_id, priority)` 로 동일 분석 내 우선순위 중복을 차단한다.

# 제약 조건

| 구분 | 내용 |
| --- | --- |
| 열거형 | `status` · `stage` · `animal_group` · `space_type` · `risk_level` · `recommendation_type` · `source` 는 CHECK 제약으로 허용 값을 제한한다. |
| 수치 범위 | 점수는 0~100, 정규화 좌표와 점유율은 0~1로 제한한다. |
| 소수 타입 | 소수 컬럼은 `DECIMAL` 을 사용한다. `FLOAT`·`DOUBLE` 은 오차가 정렬과 임계값 판정을 바꾼다. |
| 문자셋 | `utf8mb4` / `utf8mb4_unicode_ci`, 엔진은 `InnoDB` |
| 시각 | `DATETIME(6)` 에 KST로 저장한다. 연결마다 세션 타임존을 `+09:00` 으로 고정한다. |
| 상태 정합성 | `completed_at` · `error_message` 는 해당 상태에서만 값을 가진다. `stage` 는 `PROCESSING` 에서 필수이며 `FAILED` 는 실패 지점을 보존한다. |
| 마킹 이미지 | `risk_level = 'SAFE'` 이면 `marked_image_path` 는 NULL이다. |
| 우선순위 | `UNIQUE (analysis_id, priority)` 로 중복을 차단한다. |
| 외래키 | `ON DELETE CASCADE` |

성능평가로 조정되는 임계값(confidence 0.40, 탐지 프레임 수 2, 점유율 구간)은 CHECK 제약에 포함하지 않는다. 값이 바뀔 때마다 스키마 마이그레이션이 발생하기 때문이다.

같은 이유로 `progress` 의 단계별 수치도 CHECK에 넣지 않는다. 경계값(`PENDING` = 0, `COMPLETED` = 100)만 강제한다.

> ※ `CHECK` 제약은 MySQL 8.0.16 이상에서만 동작한다. 그 미만 버전은 무시하므로 애플리케이션 검증이 유일한 방어선이 된다.

상세 제약은 DB 명세서를 따른다.

# 정규화 설계 근거

3NF를 기준으로 하되, 근거가 있는 경우에만 비정규화한다. 아래는 의도적으로 정규형을 벗어난 항목이다.

## 파생 컬럼

| 컬럼 | 파생 관계 | 유지하는 이유 |
| --- | --- | --- |
| `total_score` | 항목별 점수 4종의 가중 평균 | 이력 목록을 종합 점수로 정렬·필터할 때 인덱스를 사용한다. 가중치가 바뀌어도 과거 분석 점수가 흔들리지 않는다 |
| `progress` | `stage` 와 1:1 대응 | 조회 질의가 단순해진다. 단계 정의가 바뀌어도 과거 값이 보존된다 |
| `detected_object.risk_level` | `object_name` × `animal_group` | **판정 시점의 결과를 보존한다.** 판정 규칙이 바뀌어도 이미 사용자에게 보여준 마킹 색상이 소급 변경되지 않는다 |

파생 컬럼은 원본과 어긋날 수 있다. 애플리케이션이 단일 함수를 거쳐 값을 채워 정합성을 유지한다.

## JSON 컬럼과 자식 테이블의 구분

`risk_factors` 는 JSON 컬럼이고 `recommendation` 은 자식 테이블이다. 구조가 유사한데 저장 방식이 다르므로 기준을 명시한다.

| 대상 | 구조 | 저장 | 근거 |
| --- | --- | --- | --- |
| `risk_factors` | `{text, source}[]` | JSON 컬럼 | 표시 전용. 조회·필터·정렬 대상이 아니며 행 단위 제약이 없다 |
| `analysis_result` | `String[]` | JSON 컬럼 | 표시 전용. 구조가 없는 문자열 배열이다 |
| `recommendation` | `{type, text, priority, source}[]` | 자식 테이블 | `UNIQUE (analysis_id, priority)` 로 우선순위 중복을 차단해야 한다 |

**행 단위 제약이 필요하면 테이블, 표시 전용이면 JSON** 을 기준으로 한다.

JSON 컬럼은 반복 그룹이므로 엄밀히는 1NF를 벗어난다. 다만 질의 대상이 아니므로 정규화 이득이 없고, 자식 테이블로 분리하면 조회 시 조인이 하나 늘어난다.

## 마스터 테이블을 두지 않는 대상

| 대상 | 판단 |
| --- | --- |
| `object_name` | 탐지 대상 12종이 고정 도메인이다. 매핑은 애플리케이션의 객체 코드 표가 관리한다 |
| `device_id` | 회원 기능이 없어 식별자 자체가 엔티티다. 부가 속성이 없다 |

# 데이터 흐름

```
분석 요청 접수
        │
        ▼
analysis INSERT  (status = PENDING)
        │
        ▼
[ AI 분석 파이프라인 ]
        │
        ▼
analysis UPDATE  (분석 결과)
        │
        ├──────────────┐
        ▼              ▼
detected_object   recommendation
   INSERT            INSERT
        │              │
        └──────┬───────┘
               ▼
      analysis UPDATE
      (status = COMPLETED)
```

> ※ AI 분석 파이프라인의 내부 단계는 **AI 설계서**를 따른다.
> 
> ※ 단계별 컬럼 채움 순서는 **DB 명세서**의 데이터 저장 흐름을 따른다.
