# 성능평가 진행 가이드

# 문서 개요

본 문서는 「AI 성능 평가서」의 측정을 실제로 수행하기 위한 실행 절차를 정의한다.

평가서가 **무엇을 재는지**를 정의한다면, 본 문서는 **어떤 순서로 어떻게 재는지**를 정의한다.

촬영 없이 진행한다. **COCO(정확도) + 짧은 영상(추적·시퀀스)** 이원 구성으로, 영상이 있어야만 가능한 항목(추적 · 대표 프레임 · 마킹 · `detection_frame_count` 축)까지 측정한다.

# 0. 이번 라운드의 범위

## 0.1 데이터를 둘로 나눈다

| 데이터 | 용도 | GT |
| --- | --- | --- |
| **COCO val2017 200장** | 탐지 mAP · Precision · Recall | 검수된 박스 GT **무료** |
| **짧은 영상 5~8개** | 추적 · 대표 프레임 · 마킹 · `frame_count` · open-vocab 정성 | 고유 객체 수만 세면 됨 (박스 라벨 불필요) |

영상에 박스 GT를 붙이려 하면 한 라운드가 끝난다. **mAP는 COCO에서 재고, 영상은 시퀀스가 필요한 항목에만 쓴다.**

## 0.2 영상을 넣어서 되살아나는 항목

| 항목 | COCO만 | 영상 추가 |
| --- | --- | --- |
| 객체 추적 | ✕ | **○** |
| 대표 프레임 선정 | ✕ | **○** |
| 위험 객체 마킹 | ✕ | **○** |
| 탐지 신뢰 기준 `detection_frame_count ≥ 2` | ✕ (conf만) | **○ 두 축 모두** |
| 영상 처리 성공률 | ✕ | **○** |
| 탐지 정확도 mAP | ○ (COCO GT) | ○ COCO 유지 |

## 0.3 전선 · 계단은 이번 라운드 평가에서만 제외한다

**학습 대상에서 빼는 것이 아니라 순서를 뒤로 미루는 것이다.** 최종적으로는 커스텀 학습에 포함하며, 운영 탐지 모델은 12종 전부를 한 모델로 처리한다.

| 영역 | 영향 |
| --- | --- |
| 점수 규칙 · 분석 항목 9종 | **변경 없음.** 기준값 56 / 64 / 73 유지 |
| **커스텀 데이터셋** | 측정 후 **최소 4종 / 최대 7종** 으로 압축 |
| 이번 라운드 수집 우선순위 | 창문 · 카펫 · 급식기 · 급수기 · 반려동물 침대 · 캣타워 (6종) |
| 이번 라운드 탐지 mAP 측정 | 전선 · 계단 제외 (학습 전이라 GT 없음) |
| 모델 선정 비중 | 핵심 클래스(cable) 20% → 이번 라운드만 재배분 (§6.4) |
| **슬롯 6 open-vocab** | **학습 우선순위 판단 도구** |

### 운영 모델 수는 2개로 유지된다

| 모델 | 역할 |
| --- | --- |
| 커스텀 학습 탐지 모델 1개 | 12종 전부 |
| VLM 1개 | 환경 분석 |

> ※ open-vocabulary 모델은 **평가 도구이며 운영에 포함하지 않는다.** 운영에 남기면 커스텀 모델과 두 번 추론해야 하므로 프레임당 처리 시간과 메모리가 약 2배가 된다. Mac Studio 한 대에서 VLM까지 함께 돌리는 구성에서는 동시 처리 수와 처리 제한 시간을 다시 잡아야 한다.

### open-vocab 슬롯의 목적

커스텀 후보 8종을 한꺼번에 수집할 수 없으므로 **어느 클래스를 먼저 모을지** 정하는 데 쓴다.

| 판정 | 조치 |
| --- | --- |
| 잘 찾음 | 수집 후순위. 급한 클래스부터 처리한다 |
| 못 찾음 | **선순위.** 어려운 클래스라 수집·학습에 시간이 더 걸린다 |

### 이번 라운드에서 측정할 수 없는 것

전선은 전 그룹에서 `HIGH` 이며 최소 위험도 하한이 적용되는 유일한 객체다. 학습 전이고 GT가 없어 이번 라운드에서는 정확도를 수치화할 수 없다.

점수 민감도를 실측한 결과는 다음과 같다. (소형견 · 거실 · 소파+카펫 기준)

| 상황 | 결과 |
| --- | --- |
| 전선 오탐 1건 | 종합 **−15p**. 없는 위험을 사용자에게 표시한다 |
| **전선 미탐 1건** | 종합 **+15p**. 점수가 오르면서 **실제 감전 위험을 알리지 못한다** |

미탐이 더 나쁘다. 따라서 **학습 후 라운드에서 전선의 Recall을 반드시 측정한다.** 정성 척도로는 "찾은 것"만 보이고 "놓친 것"은 보이지 않는다.

## 1.2 선별 기준

| 문제 | 영향 | 대응 |
| --- | --- | --- |
| **컷 전환 (1~2초마다 장면 변경)** | **추적이 완전히 망가진다.** 컷마다 ID가 새로 발급돼 ID Switch가 폭발한다 | **단일 컷 영상만 사용** ← 절대 조건 |

| 자막 · 스티커 · 워터마크 | 오탐 유발 | 오버레이 없는 구간 선택 |

## 1.3 컷 전환 자동 검출

눈으로 고르지 말고 스크립트로 거른다.

```bash
# 컷 전환 개수 세기 — 0이어야 추적 평가에 쓸 수 있다
for f in videos_raw/*.mp4; do
  n=$(ffmpeg -i "$f" -vf "select='gt(scene,0.3)',showinfo" -f null - 2>&1 \
      | grep -c "showinfo")
  dur=$(ffprobe -v error -show_entries format=duration -of csv=p=0 "$f")
  echo "$(basename $f)  컷전환=$n  길이=${dur}s"
done
```

```bash
# 컷이 있으면 가장 긴 단일 구간만 잘라낸다
ffmpeg -i in.mp4 -ss 3.2 -to 11.8 -c copy videos/v01.mp4
```

**목표: 컷 전환 0인 5~10초 클립 5~8개.** 하나도 못 만들면 추적 슬롯을 포기하고 나머지로 진행한다.

# 3. 슬롯 구성

절대 시각이 아니라 **순서와 소요 시간**으로 정의한다.

| 순서 | 슬롯 | 소요 | 비고 |
| --- | --- | --- | --- |
| 1 | 규칙 검증 | 10분 | **CPU만.** 다운로드와 완전 병렬 |
| 2 | 영상 선별 · 프레임 추출 | 25분 | 컷 검출 → 클립 확정 → 고유 객체 수 |
| 3 | 객체 탐지 3종 | 30분 | **단독 실행.** 다운로드 중지 |
| 4 | 탐지 신뢰 기준 | 30분 | conf × `frame_count` 두 축 |
| 5 | 추적 · 대표 프레임 · 마킹 | 30분 | |
| 6 | open-vocab | 30분 | **이번 라운드에서 격상** |
| 7 | 환경 분석 VLM | 30분 | 받은 모델만 |
| 8 | 집계 | 30분 | |

**규칙 검증을 맨 앞에 두는 이유가 둘이다.** ① 실패해도 뒤 슬롯이 도는 동안 고칠 수 있다 ② CPU만 쓰므로 다운로드·영상 확보와 완전 병렬이다.

**탐지 슬롯 동안만 다운로드를 멈춘다.** 속도·메모리를 재는 유일한 슬롯이라 네트워크·디스크 부하가 숫자를 오염시킨다.

> ※ 어느 슬롯이든 소요 시간을 초과하면 다음 슬롯으로 넘어간다. 버퍼가 없다.

## 4.3 cable 점수 민감도 — 실측 완료

소형견 · 거실 · 점유율 0.35 기준이다.

| 탐지 결과 | 안전성 | 종합 |

## 6.2 통일 채점

```python
from pycocotools.coco import COCO
from pycocotools.cocoeval import COCOeval

def score(gt_json, pred_json, cat_ids):
    gt = COCO(gt_json); dt = gt.loadRes(pred_json)
    e = COCOeval(gt, dt, "bbox"); e.params.catIds = cat_ids
```

## 6.3 속도 측정

```python
import time, torch

def bench(predict_fn, img, warmup=20, runs=200):
    for _ in range(warmup): predict_fn(img)
    torch.mps.synchronize()                 # 없으면 과소 측정
    t0 = time.perf_counter()
    for _ in range(runs): predict_fn(img)
    torch.mps.synchronize()
    ms = (time.perf_counter()-t0)/runs*1000
    return {"ms": ms, "fps": 1000/ms,
            "peak_gb": torch.mps.driver_allocated_memory()/1e9}
```

# 7. 슬롯 4 — 탐지 신뢰 기준

영상이 있으므로 `detection_frame_count` 축을 함께 측정한다.

```python
CONF_GRID, COUNT_GRID = [.20,.25,.30,.35,.40,.45,.50], [1,2,3]

def accept(dets, conf_th, count_th):
    kept = [d for d in dets if d["score"] >= conf_th]        # 프레임 단위 필터
    per_obj = defaultdict(list)
    for d in kept:
        per_obj[(d["video"], d["track_id"])].append(d)
    return {k:v for k,v in per_obj.items() if len(v) >= count_th}   # 객체 단위 필터

rows = []
for c in CONF_GRID:
    for n in COUNT_GRID:
        acc = accept(RAW_VIDEO, c, n)
        rows.append({"conf": c, "count": n,
                     "채택객체수": len(acc),
                     "제거객체수": len(BASE) - len(acc),
                     "점수변동폭": abs(score_with(acc) - SCORE_BASE)})
```

기준선은 `conf=0.001`, `count=1` 이다.

## 7.1 GT 없이 정탐·오탐을 가르는 법

박스 GT가 없으므로 자동 채점이 안 된다. **필터로 제거된 객체만 육안 판정한다.**

```
conf=0.40, count=2로 필터 → 제거된 객체 목록 출력
  → 각 객체의 대표 프레임을 잘라서 나열
  → 사람이 "실제 있었다 / 없었다" 판정
       실제 있었음 = 정탐 손실
       없었음      = 오탐 제거 성공
```

제거되는 객체는 보통 수십 개 수준이라 10분이면 판정된다. **전체 객체를 다 볼 필요가 없다는 것이 요령이다.**

## 7.2 확정 / 미확정

| 확정 | 미확정 |
| --- | --- |
| 스윕 스크립트 (conf × `frame_count` 두 축) | 임계값 0.40 / 2의 최종 값 |
| 곡선 형태, 점수 변동폭 계산 경로 | 커스텀 클래스 confidence 분포 |
| `frame_count` 를 늘렸을 때의 실제 효과 | |

> ※ 학습 전 COCO 가중치의 confidence 분포는 파인튜닝 후와 다르다. **이번 라운드에서 나온 최적값을 확정하면 안 된다.** 목적은 스크립트를 완성하는 것이고, 학습 후 같은 스크립트로 값을 뽑는다.

## 8.1 대표 프레임 · 마킹

결정성·동점 처리는 슬롯 1에서 검증한다. 여기서는 **생성 품질만** 본다.

| 대표 프레임 | 방법 |
| --- | --- |
| 선정 성공률 | 생성 성공 / 전체 |
| 객체 포함률 | 대표 프레임 객체 **종류 수** / 영상 전체 탐지 종류 수 |
| 동점 발생 빈도 | 동점 영상 / 전체 |

선명도는 측정하지 않는다. 평가서에서 제외된 항목이다.

| 마킹 (육안, 3점) | 기준 |
| --- | --- |
| Bounding Box 정확도 | 2 = 정확 / 1 = 어긋남 / 0 = 엉뚱 |
| 위험도 표시 정확도 | 2 = 판정표 일치 / 1 = 일부 불일치 / 0 = 반대 |
| 사용자 가독성 | 2 = 바로 이해 / 1 = 설명 필요 / 0 = 혼란 |

**SAFE 객체가 화면에 그려지지 않는지 이미지로 다시 확인한다.** 코드 레벨로 통과했어도 시각화 단계에서 다시 그리는 경우가 있다.

| --- | --- |
| `NOT_JSON` | 코드펜스·설명 문장을 걷어내도 JSON 이 아니다 |
| `MISSING_FIELD` | `riskFactors` · `analysis` · `recommendations` 중 누락 |
| `BAD_SHAPE` | 항목 구조가 형식과 다르다 |
| `BAD_TYPE` | `recommendations[].type` 이 정의된 4종이 아니다 |
| `BAD_SOURCE` | `source` 가 `DETECTED` · `OBSERVED` 가 아니다 |
| `TOO_FEW_ANALYSIS` | `analysis` 가 2건 미만 |
| `NO_RECOMMENDATION` | `recommendations` 가 0건 |

**부족은 거절이고 초과는 복구다.** 없는 내용을 만들어 채울 수는 없지만, 넘치는 것은 잘라내면 된다.

### 복구 — 재호출 없이 통과하는 위반

| 항목 | 처리 |
| --- | --- |
| `STRIPPED_FENCE` | 코드펜스 제거 |
| `EXTRACTED_OBJECT` | 앞뒤 설명 문장에서 JSON 객체만 추출 |
| `IGNORED_SCORE` | 모델이 만든 `petFitScore` 를 무시 |
| `DEMOTED_TO_OBSERVED` | 근거 없는 `DETECTED` 를 `OBSERVED` 로 강등 |
| `DEDUPED_RISK_FACTORS` | 중복 위험 요소 병합 |
| `TRUNCATED_RISK_FACTORS` | 5건 초과분 절단 |
| `TRUNCATED_ANALYSIS` | 4건 초과분 절단 |
| `TRUNCATED_RECOMMENDATIONS` | 5건 초과분 절단 |
| `RENUMBERED_PRIORITY` | `priority` 를 1부터 다시 매김 |

### 5번 항목은 자동으로 판정된다

이전 판에는 "`text` 가 자유 서술이라 자동 판정 불가, 육안 채점" 으로 적혀 있었다. **틀렸다.** 구현은 객체명을 추출하지 않고 **서술에 이름이 들어 있는지만** 본다.

```python
if any(name in text for name in names):
    return source
repairs.add(Repair.DEMOTED_TO_OBSERVED)
return RiskSource.OBSERVED
```

강등하되 삭제하지 않는다. 탐지 목록에 없어도 이미지에서 확인했을 수 있고, `OBSERVED` 는 점수에 영향을 주지 않으므로 잘못 강등해도 Pet Fit Score 의 재현성은 유지된다. 육안 채점 몫이 8건 줄어든다.

### 합격선

| 지표 | 산출 | 합격선 |
| --- | --- | --- |
| **첫 호출 통과율** | `regenerations == 0` 인 시나리오 비율 | **8/8 중 7 이상** |
| 최종 통과율 | 재생성 소진 없이 결과를 얻은 비율 | **8/8** |
| 복구 발생률 | 복구 항목이 하나라도 걸린 비율 | 기록만. 감점 없음 |
| 복구 항목 분포 | 항목별 발생 건수 | 모델 간 형식 안정성 비교 |

**최종 통과율이 8/8 미만이면 그 모델은 후보에서 제외한다.** 재생성 3회를 소진하면 사용자에게 분석 실패가 나간다.

> ※ 복구는 감점하지 않되 반드시 기록한다. 어떤 항목이 자주 걸리는지가 프롬프트를 고칠 근거가 된다. 특정 항목이 8/8에서 발생하면 프롬프트 설계서의 해당 지시문이 약한 것이다.

**OBSERVED** 는 이미지와 대조해 정탐 / 오탐 / 과장으로 나눈다. **발견 가치**(탐지 대상 밖 위험 요소를 정확히 짚은 건수)를 따로 센다.

> ※ 2인이 평가하면 시나리오로 나누되 **모델로 나누지 않는다.** 평가자 성향이 모델 점수로 둔갑한다.

**루브릭 12점** — 환경 분석 품질 4 / 추천 실행 가능성 4 / 점수 정합성 2 / 한국어 자연스러움 2. 침실 시나리오에서 급식·급수를 지적하면 점수 정합성 실패다.
