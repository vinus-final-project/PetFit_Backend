# 작업 분담

# 문서 개요

본 문서는 Pet Fit 프로젝트의 남은 작업을 정의하고 5인 팀의 담당 범위를 나눈다.

파일 충돌을 줄이기 위해 **기능이 아닌 디렉터리 단위로 소유권을 나눈다.** 기능 단위로 자르면 여러 명이 같은 파일을 동시에 수정하게 된다.

## 경계는 세 곳이다

규약마다 양쪽이 서로의 내부를 모른다. 구현이 바뀌어도 반대편은 수정하지 않는다.

| 규약 | 가르는 것 | 스텁 |
| --- | --- | --- |
| `ai/pipeline.py` 의 `Pipeline` | 서비스 ↔ AI | `StubPipeline` |
| `ai/vision/detector.py` 의 `Detector` | Vision ↔ 탐지 모델 | `StubDetector` |
| `ai/llm/base.py` 의 `VisionLLM` | 환경 분석 ↔ 생성 모델 | `FakeLLM` |

세 스텁을 끼우면 **모델 없이 영상에서 최종 결과까지** 검증된다.

## AI 워커 스텁을 먼저 만든 이유

프론트가 1명인데 서버 응답이 없으면 화면만 만들고 멈춘다.

스텁은 실제 AI 대신 **고정된 가짜 탐지 결과**를 넣고 점수는 완성된 `score_generator` 를 그대로 쓴다. 이것만 있으면 아래가 즉시 검증된다.

- `PENDING → PROCESSING → COMPLETED` 상태 전이와 진행률 폴링
- 실패 처리와 재시도 3회 제한
- 점수 산출 → DB 저장 → 조회 왕복
- 프론트의 실제 응답 기반 화면 개발

AI 성능평가가 끝나면 **워커 내부만 교체**한다. API·DB·프론트는 수정하지 않는다.

## 상태와 진행률 규칙

`progress` 는 `stage` 에서 파생되는 값이다. 컬럼에 직접 대입하지 않는다.

```python
from app.schemas.enums import progress_for
progress = progress_for(status, stage)
```

`FAILED` 는 실패한 단계를 그대로 보존한다. 클라이언트가 재촬영과 재시도 중 무엇을 안내할지 이 값으로 분기한다.

> **상태 : 코드 구현 완료.** `app/ai/vision/` 8개 파일, 테스트 211건이 통과한다.

| 단계 | 작업 |
| --- | --- |
| 1 Video Processor | 해상도 축소, 형식 검증 |

| 4 Occupancy Calculator | 프레임별 점유율 + 중앙값 (합집합 면적 함수 완성됨) |

## 학습 데이터셋 구축

**측정 결과로 대상이 좁혀졌다.** open-vocabulary 판정과 오탐 간섭 측정을 교차해 클래스를 세 등급으로 나눈다.

### 수집 대상

| 등급 | 클래스 | 근거 |
| --- | --- | --- |
| **필수** | **전선 · 계단** | 평가 미실시. 전선은 전 그룹 `HIGH` |
| **필수** | **창문** | open-vocab mAP **0.056** — 두 모델 다 참패 |
| **필수** | **급수기** | Recall **0.33** |
| 조건부 | 캣타워 | Recall 0.76이나 `chair` 오탐 **35%**. 아래 참고 |
| 보류 | 카펫 · 급식기 | mAP 0.96~0.98이나 **데이터 편향으로 신뢰 불가** |
| 불필요 | 반려동물 침대 | Recall 0.58 · 오탐 0.03 |
| 제외 | 소파 · 침대 · 의자 · 테이블 | COCO 재사용 |

**최소 4종, 최대 7종.** 카펫·급식기는 실내 장면으로 재측정한 뒤, 캣타워는 아래 판단 후 확정한다.

### 카펫 · 급식기를 보류하는 이유

측정에 쓴 데이터가 실제 사용 조건과 달랐다.

| 클래스 | 데이터 문제 |
| --- | --- |
| 카펫 | 박스가 이미지 평균 **57%를 덮는 클로즈업**. 실내 장면이 아님 |
| 급식기 | 타임스탬프가 **76초 구간에 집중**, 전 이미지 412×412 동일 크롭 → 단일 장면 |

원 측정 문서도 급식기를 **"성능 수치로 사용 불가, 반응 여부 확인용"** 으로 적고 있다. 실내 사진으로 다시 재면 값이 떨어질 가능성이 높다.

### 캣타워 — 미탐 시 손실이 크다

메인 탐지기가 캣타워를 `chair` 로 **35% 오탐**한다. 문제는 중복 집계가 아니라 **캣타워가 목록에서 빠지는 것**이다.

| 그룹 | 활동성 | 종합 |
| --- | --- | --- |
| **고양이** | 100 → 40 (**−60p**) | 92 → 77 |
| 소형견 | 100 → 67 (−33p) | 92 → 84 |
| 중대형견 | 100 → 75 (−25p) | 92 → 86 |

수직 공간은 고양이에게 `●●` 다. 리스크를 감안해 **학습 대상에 포함하는 쪽을 권한다.**

> ※ 반대 방향(캣타워를 의자로도 함께 집계)은 점수에 영향이 없다. `의자` 는 감점 근거 객체 10종에 포함되지 않는다.

### 수집 방식 — 점진적 확대

500장을 한꺼번에 모으지 않는다. **어느 클래스에 얼마가 필요한지가 아직 데이터로 확인되지 않았다.**

```
1차: 클래스당 50장 → 학습 → 클래스별 mAP 측정
        ↓
   목표 미달 클래스만 추가 수집
```

4종 × 50장이면 200장으로 하루 이틀 작업이다. 결과를 보고 늘리는 편이 무작정 500장을 모으는 것보다 낫다.

> ※ **"장"과 "인스턴스"는 다르다.** 사진 1장에 창문 3개면 3 인스턴스다. 창문·카펫은 한 장에 여러 개가 나오지만 급수기·캣타워는 보통 1장에 1개다.

| 항목 | 내용 |
| --- | --- |
| 라벨링 형식 | YOLO (class_id, x_center, y_center, width, height), 정규화 0.0~1.0 |

# 성능평가 — 1차 측정 완료

## 선정 결과

| 파트 | 선정 | 근거 |
| --- | --- | --- |
| 객체 탐지 | **YOLO26-m** | 정확도 RF-DETR과 동률(0.08%p 차) → **속도 2.5배** |
| open-vocab | **YOLOE-26** | 9개 지표 중 8개 우세 |
| 객체 추적 | BoT-SORT (**잠정**) | ID Switch 22% 감소. 게이트 미달로 재측정 필요 |
| 환경 분석 VLM | **미측정** | — |

측정 조건은 HomeObjects-3K validation 404장, COCO 사전학습 가중치 기준이다. 상세는 **「모델 선정 근거」** 를 따른다.

## 지금 코드에 반영할 수 있는 것

| 항목 | 값 |
| --- | --- |
| `YOLO_MODEL_PATH` | `./models/yolo26m.pt` |
| 프레임워크 | ultralytics 단일 API (탐지·추적·open-vocab 통일) |
| Vision 처리 시간 | 30프레임 **0.67초** — 180초 예산의 0.4% |
| 탐지 Peak 메모리 | 1.22GB → 동시 2건 + VLM 32B도 24.4GB로 여유 |

**병목은 Vision이 아니다.** 180초 타당성은 VLM 측정에 달렸다.

## 트래커 게이트 미달의 실제 영향

중복 제거 정확도 0.287로 게이트(85%)에 크게 미달한다. 다만 **점수에는 영향이 없다.**

| 영역 | 영향 |
| --- | --- |
| Pet Fit Score | **없음** — 점수는 개수가 아니라 **존재 여부**로 판정한다 |
| 활동 공간 점유율 | 거의 없음 — 합집합 면적이라 중복 박스를 한 번만 센다 |
| `detectedObjects` 응답 | 침대 1개가 11건으로 나열됨 |
| 마킹 이미지 | 위험 객체면 중복 수만큼 생성 |

> ※ 원 측정 문서는 "Pet Fit은 객체 개수로 점수를 산출한다"고 전제했으나, 구현은 존재 여부 기반이다. 침대 1개와 11개의 종합 점수가 동일함을 확인했다.

## 아직 확정되지 않은 값

| 항목 | 현재 값 | 근거 |
| --- | --- | --- |
| 활동 공간 점유율 임계값 | 0.40 / 0.60 / 0.75 | 실측 없이 설정한 초기값 |
| 점유율 대표값 | 중앙값 | 평균·최댓값과 비교 후 확정 |
| 프레임 단위 confidence | 0.25 | YOLO 기본값 |
| 객체 채택 confidence | 0.40 | 오탐·미탐 균형 미검증 |
| 최소 탐지 프레임 수 | 2 | 초기값 |
| 프레임 추출 간격 | 초당 3프레임 | 객체 누락률 측정 후 조정 |
| 서버 동시 처리 수 | 2건 | 메모리·완료 시간 측정 후 조정 |
| 처리 제한 시간 | 180초 | 실제 소요 시간 측정 후 조정 |
| 업로드 크기 상한 | 100MB | 촬영 영상 크기 분포 확인 후 조정 |
| 클래스당 인스턴스 수 | 500 / 1,500 | 클래스별 난이도에 따라 조정 |
| 최종 탐지 객체 | 12종 | 성능이 낮은 클래스는 제외 검토 |

confidence·프레임 수·점유율 임계값은 **스윕을 실행하지 않아** 초기값 그대로다. 학습 후 같은 스크립트로 확정한다.

**규칙 검증은 이미 자동화되어 있다.** 테스트 **914건**이 통과 중이며, 평가 항목 19개 중 14개를 커버한다.

```
python -m pytest
```

| 구성요소 | 상태 |
| --- | --- |
| Occupancy Calculator · Object Name Mapper · Risk Classifier · Score Generator | **구현 + 검증 완료** |
| Detection Filter | 미구현 |

> ※ 원 측정 문서는 규칙 검증 5종을 "구현 전이라 미측정"으로 적었으나, 4종은 이미 완료되었다. 다시 하지 않는다.

실행 절차는 **「성능평가 진행 가이드」** 를 따른다. 데이터 준비 · 슬롯 구성 · 측정 스크립트가 정의되어 있다.

## 전선 · 계단 처리

**학습 대상에서 빼는 것이 아니라 순서를 뒤로 미룬다.** 최종적으로는 커스텀 학습에 포함한다.

| 영역 | 영향 |
| --- | --- |
| 점수 규칙 · 분석 항목 9종 | **변경 없음.** 기준값 56 / 64 / 73 유지 |
| 커스텀 데이터셋 | 측정 후 **최소 4종 / 최대 7종** 으로 압축 |
| 이번 라운드 탐지 mAP | 두 클래스 제외 (학습 전이라 GT 없음) |
| 모델 선정 비중 | 핵심 클래스 20% → 이번 라운드만 재배분 |

### 운영 모델 수

| 모델 | 역할 |
| --- | --- |
| 커스텀 학습 탐지 모델 1개 | 12종 전부 |
| VLM 1개 | 환경 분석 |

> ※ open-vocabulary 모델은 **평가 도구이며 운영에 포함하지 않는다.** 운영에 남기면 커스텀 모델과 두 번 추론해야 하므로 처리 시간과 메모리가 약 2배가 된다.
> 
> ※ 전선은 전 그룹 `HIGH` 이며 최소 위험도 하한이 적용되는 유일한 객체다. 미탐 1건이 종합 점수를 **15p 올리면서** 실제 위험을 알리지 못한다. 학습 후 라운드에서 Recall을 반드시 측정한다. 상세는 가이드 §0.3.

# 공통 규칙

## 개발 환경

```
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt
python -m pytest
```

테스트 914건이 통과하면 정상이다.

`.env` 는 저장소에 없다. 각자 아래 항목을 채워 만든다.

```
DB_USER, DB_PASSWORD, DB_HOST, DB_PORT, DB_NAME
STORAGE_ROOT, YOLO_MODEL_PATH, LLM_PROVIDER, LLM_API_KEY
```

## 데이터베이스

```
python -m scripts.init_db          # 스키마·테이블 생성 후 검증
python -m scripts.init_db --check  # 상태만 확인
python -m scripts.init_db --drop   # 전체 삭제 후 재생성 (개발 전용)
```

스키마 정본은 `app/models/` 이다. `migrations/001_initial.sql` 은 파생물이므로 직접 수정하지 않는다.

```
python -m scripts.gen_ddl > migrations/001_initial.sql
```
